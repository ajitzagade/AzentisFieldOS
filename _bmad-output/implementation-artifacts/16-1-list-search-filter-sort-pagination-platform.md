# Story 16.1: List Search, Filter, Sort & Pagination Platform

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As Owner/Admin,
I want every list page to load one page at a time with search, filters, and sortable columns,
so that the system stays fast and scannable at hundreds or thousands of records instead of degrading into one unbounded, unscannable table.

## Acceptance Criteria

1. **Given** a list with more records than the default page size, **when** I open it, **then** only the first page loads from the server, with Previous/Next controls and a "showing X–Y of Z" indicator — never the whole table fetched up front, and never infinite scroll (explicitly banned per `EXPERIENCE.md`'s interaction contract — pagination controls only).
2. **Given** I type in a list's search box, **when** I pause typing (debounced), **then** results filter server-side against that list's defined searchable fields, and the page resets to 1.
3. **Given** a list has a meaningful filter dimension for it (Status, Site, Category, Vendor, date range — varies per list), **when** I choose a filter value, **then** results narrow server-side, combinable with search and each other.
4. **Given** I click a sortable column header, **when** the request re-runs, **then** results re-sort server-side ascending/descending, with a visible indicator on the active sort column.
5. **Given** a list has zero records at all vs. zero records matching the current search/filters, **when** either happens, **then** two distinct empty states show ("nothing recorded yet" with the existing create-first-entry prompt vs. "no results match your filters" with a "Clear filters" action) via `DataTable`'s existing empty state (AD-6) — never a bespoke state per page.
6. **Given** a request is loading or fails, **when** the state changes, **then** `DataTable`'s existing loading/error states render unchanged — no second state machine.
7. **Given** no new query params are passed to a changed endpoint, **when** it's called by any existing caller, **then** the response matches today's unbounded full-list behavior exactly — every change is additive, never a breaking default.
8. **Given** a list page is loaded with `?q=&page=&sort=&<filter>=` in the URL, **when** the page is reloaded or the URL is shared, **then** the same search/filter/sort/page state is reproduced — the URL is the source of truth, not component-local state.

## Dev Notes

- **This story is pure additive platform work — no existing data model changes.** No Prisma schema/migration is expected; this is Prisma query shape (`findMany` → `findMany` + `skip`/`take`/`orderBy` + `count`) and API/UI surface changes only.
- **AD-5 discipline is the point of this story**: one pagination control, one sort-header mechanism, one URL-sync hook — never a bespoke pager per list page. If Task 3 (Sites) produces something that doesn't generalize cleanly to Task 4 (Movements) or Task 5's other lists, fix the shared primitive, don't fork it.
- **AD-7 discipline**: the query-param schema is defined once per list shape (or one generic factory, per Task 1) in `packages/shared`, imported by both apps — not hand-rolled per page.
- **Banned pattern (`EXPERIENCE.md` line 108)**: infinite scroll is explicitly banned everywhere in this product — pagination controls only. Do not implement a "load more"/intersection-observer pattern even if it seems simpler for one list.
- **The Movements page (Task 4) is the real risk in this story** — everything else is a mechanical repeat of the Sites pattern. Budget the most review/testing attention there; see Task 4's explicit architectural decision point.
- **Backward compatibility is a hard constraint, not a nice-to-have** (AC #7): these are live production endpoints (`sandeepent.azentis.in`) already called by existing pages during this same story's own migration and potentially by code outside this story's scope. An endpoint changed in Task 3/4/5 must behave identically to today when called with no new params.
- Do not build a generic, all-purpose "DataTable v2" that tries to anticipate every future list's needs — build exactly what Sites and Movements need in Tasks 3–4, and only generalize further if Task 5's remaining lists genuinely can't reuse it as built.
