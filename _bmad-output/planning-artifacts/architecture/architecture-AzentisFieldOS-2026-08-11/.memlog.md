- (decision by user) PARADIGM-DEFINING: multi-tenancy is achieved by deployment isolation, not shared-database logic. Each contractor client gets a fully separate, independently-deployed instance of the product (own frontend deployment, own database) rather than one shared app with logical tenant_id/RLS scoping. This reverses the earlier RLS-vs-app-layer framing entirely — there is no shared database to isolate within.
- (decision by user) Hosting/provisioning model: PaaS-per-tenant, not raw-cloud-org-per-tenant. Each tenant = own Vercel project (own domain/branding/env config) + own managed Postgres instance (Neon/Supabase-class provider). Chosen over AWS/GCP Organizations + Terraform because a small/AI-agent-built team can operate git-push deploys reliably but not N sets of hand-rolled cloud IAM/networking.
- (decision by user) API layer: REST/OpenAPI via NestJS (not tRPC) — user chose the more conventional, framework-enforced structure over same-monorepo type inference, keeping the door open to non-TS or partner API consumers later.
- (decision by user) Monorepo tool: Turborepo (not Nx) — right-sized for one team's frontend+backend+shared-packages repo.
- (decision by user) Styling/component system: Tailwind CSS (as the single design-token source) + shadcn/ui-style copy-in components (not a runtime UI kit like MUI/Ant, not fully custom-from-scratch) — chosen specifically to satisfy the 'no generic/template-like appearance' requirement while still giving consistent, accessible, reusable base components.
- (decision by user) Auth: managed provider (Clerk) over roll-your-own sessions/bcrypt — avoids hand-rolled security code (password hashing, session handling, MFA) that the PRD's adversarial review specifically flagged as high-risk (NFR-8, Platform Operator MFA requirement).
- (direction) Consequence of the deploy-per-tenant pivot: ORM choice reopens. Drizzle was leaned toward earlier specifically for native Postgres RLS support; RLS is now moot since each tenant has a physically separate database. Reverting the lean to Prisma — most widely used TS ORM, best AI-agent training-data familiarity, strong DX — unless the user objects.
- (direction) Frontend framework: Next.js (App Router) treated as confirmed by implication, not asked as a separate fork — the user's own choices (Vercel hosting, Tailwind+shadcn which is the de facto Next.js/React ecosystem pairing, Turborepo which is Vercel-owned) all converge on it. Stated plainly to the user as the assumed pick, open to correction.
- (question) PRD FR-52 (Tenant provisioning) and FR-53 (Tenant-scoped everything) were written assuming a shared app with a Platform Operator role inside it. Under deploy-per-tenant, there is no single running app spanning tenants — provisioning becomes an infra/deployment procedure, not an in-app feature, and 'tenant-scoped everything' becomes true by construction (separate deployments) rather than by application-layer enforcement. The PRD will need a companion update after this spine is finalized to keep FR-52/53 and NFR-1's wording accurate to how the system actually achieves isolation, per architecture's own guidance to offer updating a source input that gets overridden.
