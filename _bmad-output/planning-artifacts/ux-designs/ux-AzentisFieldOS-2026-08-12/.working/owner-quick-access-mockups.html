Two changes, not one: entity search stops being Sites/Materials-only — Vendors, Team Members, Payments, Purchases, Subcontractors, RMC entries, and Expenses each become their own grouped, searchable result set, same "See all" mechanism already used for Sites/Materials. Separately, Actions is a small, hand-curated list (one entry per primary flow — New Daily Report, Record Payment, Record Advance, Add Purchase/Vendor/Team Member/Subcontractor, Review & Price, Open Reports, Open Settings) matched by plain-text title/keyword, same mechanism as every entity group — no fuzzy AI matching, consistent with the Help Search pattern already in the spine. Actions always renders above entity groups when a query matches both, since "do a thing" beats "find a record" for intent-shaped queries. Selecting an action that needs a target (Record Payment, Record Advance) opens the D4 quick-entry modal instead of navigating away, so the palette becomes the fast path end-to-end.

D7

Action-button row alignment (confirmed real bug)

You flagged buttons "not properly visible / alignment issues" on mobile. I ran the app locally (Owner + Supervisor, 390px viewport) and traced it to source. Root cause: header action-button groups use flex flex-wrap with no rule to stack full-width below a mobile breakpoint. When 3+ buttons of different label lengths wrap on a narrow screen, each wrapped line re-justifies independently — producing a jagged, unevenly-spaced staircase instead of a clean list.

Scope: this is one shared pattern, not a per-page bug — the same flex flex-wrap ... gap-2 action-button group appears on at least a dozen pages (Movements, Site detail, Team & Labour, Vendors, Subcontractors, Machinery & Vehicles, Inventory, Expenses, Materials, Daily Activity, RMC). The fix is a single responsive rule (stack full-width below sm, wrap inline at sm and above) applied everywhere that pattern is used — not 12 separate fixes. Desktop is unaffected; this is mobile-only.
Checked and ruled out: the screenshots also showed a small floating black circle with an "N" in the bottom-left corner on several pages. That's Next.js's own local dev-mode build indicator (shows "Compiling…"/"Rendering…" during development) — it does not render in a production build, so it's not a real product bug and needs no fix.
D8

Tables still missing mobile card mode

A secondary finding while investigating D7 — you said no overflow issues, and the screens you're likely looking at (Payments, RMC, Expenses, Movements, Waste & Disposal) are fine, since those five already got mobileCard mode in the epic-17 pass. But four list tables never did, and horizontal-scroll on a 390px screen: Sites, Vendors, Team & Labour, and Inventory's stock tables. Easy to miss since there's no visible scrollbar hint — the last column just quietly runs off-screen.

  • apps/web/app/(app)/sites/sites-list-client.tsx — Site / Location columns, Location value clipped
  • apps/web/app/(app)/vendors/vendors-list-client.tsx — Vendor / Contact person / Phone, Phone clipped
  • apps/web/app/(app)/team/team-members-list-client.tsx — Name / Role / Employment Type, Employment Type clipped
  • apps/web/app/(app)/inventory/page.tsx — both the Godown Stock and Site Stock tables, Qty column clipped
Fix is already proven out: the shared DataTable component (packages/ui/src/components/data-table.tsx) already supports a mobileCard prop — it's exactly what Payments/RMC/Expenses/Movements/Waste use today. These four just need that prop wired up with the right primary/secondary field mapping per table, following the same pattern already established. No new component, no new design work.
Deferred, not designed here: Vendor payment recording and Subcontractor Site Contract UI are real gaps the audit surfaced, but both need new API/backend work, not just navigation changes — logged for a separate future round rather than folded into this quick-access pass. Say the word if you'd rather pull one in now.
